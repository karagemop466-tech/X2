Capture ledger — one row per read, with its hash

The payload hash is over the canonical rows (sorted team|player|position|injury|practice|game status), so an identical read on a later day has an identical hash and a moved page does not; sha256_capture_file hashes the stored transcription itself. Both hashes are computed over a transcription, not over HTTP bytes — the fetch surface returns processed text, so neither hash can prove what the server sent (flag F100). fields_corrected is the count of cells where a later official read overrode the transcription; the raw capture keeps what was read.

Cross-check: two readers of one render

Two sessions transcribed the same page seven minutes apart, without coordination, and the comparison is the only control in this repository that can catch a mis-transcription — as opposed to a source change or an arithmetic slip. It caught one: 1 field of 1,388 compared cells disagreed (4 fields per player: position, injury, practice_status, game_status). Applied corrections: 1. Settled by a third read of the live page (chunk 1 of 8, 2026-11-18, taken after both transcriptions were written), which renders 'Limited Participation in Practice' with an empty Game Status cell: this session's transcription was wrong. What the published table currently equals

Computed by script, not asserted: data/injuries_week10_2026.csv (347 rows) equals CAP-02 (the 2026-11-18 read, after the correction). Until session d0ede22d re-published it on 2026-11-18 it equalled CAP-01 exactly, which is what the earlier verification rows on Verification were describing; a claim of that kind should always carry the read date of both sides (flag F106).

Cadence hazard (F94). The hub ignores its own week parameter: https://www.nfl.com/injuries/?season=2026&week=11&type=REG rendered the Week 10 tables on 2026-11-18, four days after those games, while the club records printed beside them already showed post-Week-10 forms (BUF 8-1, NE 5-5). A capture job keyed on the URL would store the same week twice and label it the new one, and would mix two dates inside one row. Any scheduled capture must store the rendered Injuries - WEEK n heading — the Week label rendered column above — and fail when it is not the week it meant to capture.
