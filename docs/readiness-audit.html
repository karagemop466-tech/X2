Readiness mapping audit

The landing page publishes a decision-readiness table and says of it: “One row per requirement in the requirements register”. This page tests that sentence against the two registers themselves, row by row, and republishes the result with file line numbers so every row can be checked by hand. Nothing here is a claim about football; it is a measurement of the repository.

Why this check needs no official source. Flag F130 records that www.nfl.com is unreachable from this build environment. That does not weaken this audit: both inputs are files already in the repository, and the comparison is a string comparison anyone can re-run with python3 scripts/readiness_audit.py. No value on this page is an NFL datum.

4. One more collision the same reading turned up: the label “D01” means two things

While checking the readiness IDs, the same identifier shape appears in a second register for a completely different object. On Decision path, D01 is the first gate that must be answered (“Do we have written permission…”). On this site’s landing page, D01 is the first readiness row (the price-snapshot store). Ten labels are shared this way. Nothing is wrong with either register on its own; the risk is a reader carrying “D01” from one page to another and landing on a different object. This is recorded, not renumbered — renumbering a register that existing flags and pages already cite is the owner’s call (F132).

4. What this page does not do

  • It does not re-map, renumber, delete or merge any register row. Both registers are published exactly as their owners left them, and data/readiness_mapping.csv is unchanged.
  • It does not decide which register is canonical. That is a decision for the owner, and it is listed as such on the decisions page.
  • It does not verify any NFL value. No official page was read for this page (F130).
